### 3.1 随机交叉验证

另写一个思路完全不同的参照算法：从起始日期开始逐日向后扫描，把每一天的公历日期转换成农历，检查是否命中生日。它与被测实现方向相反（公历→农历 vs 农历→公历），也不依赖"候选年份 Y−1、Y、Y+1"的推理。用固定种子生成 600 组随机输入（公历 / 农历各约一半，农历中约 1/5 为闰月出生，日期覆盖三十；起始日期覆盖 2020—2034 年），两者结果必须完全一致。

### 3.2 变异测试

为确认测试确实能发现错误，人为在实现中植入以下缺陷，每次只植入一个并运行测试：

| 植入的缺陷 | 测试结果 |
|---|---|
| 农历候选年份去掉 Y−1 | 2 个用例失败（含随机交叉验证） |
| 农历候选年份去掉 Y+1 | 2 个用例失败（含随机交叉验证） |
| 三十出生遇小月不回退到二十九 | 2 个用例失败（含随机交叉验证） |
| 平年 2 月 29 日不回退到 2 月 28 日 | 3 个用例失败（含随机交叉验证） |
| 农历年表换算偏移一天 | 6 个用例失败 |
| 忽略闰月 | 2 个用例失败（含随机交叉验证） |

所有缺陷都被发现。

> 过程记录：交叉验证最初使用的线性同余随机数取的是低位（`seed % n`），而模 2 的幂的线性同余生成器低位周期极短，`rand(2)` 只是 0、1 交替，导致 600 组用例覆盖面很差，植入"去掉 Y−1"的缺陷时随机测试没有失败。改为取高位后，随机测试能够发现上表全部缺陷。

## 6. 性能

生日查询对全班 n 人逐个计算，复杂度 O(n)。实测农历生日计算的耗时：

| 场景（50 个农历生日，一次查询） | 优化前 | 优化后 |
|---|---|---|
| 首次 | 约 120 ms | 约 14 ms |
| 后续 | 约 85 ms | 约 2.5 ms |

优化前的瓶颈在于农历库只缓存最近一个年份，而算法需要交替查询三个年份；优化方法见系统设计 3.4 节。

## 7. 测试中发现并修复的问题

| 问题 | 原因 | 处理 |
|---|---|---|
| 农历生日查询慢（50 人约 85ms） | 农历库单年份缓存被交替访问击穿 | 按农历年缓存月表，查表换算 |
| Windows 上部署时初始化数据失败（`has no exported member`） | 依赖 `@prisma/client` 安装钩子生成客户端，失败被静默吞掉 | 显式生成并校验，见第 8 节 |
| 后台服务异常退出后不会重启 | 任务计划程序的"失败时重新启动"不覆盖程序以非 0 退出码结束的情况 | 启动器自行守护重启，见第 8 节 |
| 随机交叉验证未发现植入的缺陷 | 随机数取低位，周期过短 | 改为取高位 |
| 未登录时返回英文提示 "Unauthorized" | 框架默认异常信息 | 自定义 JWT 守卫，返回"请先登录""登录已过期" |
| 按钮操作中接口报错时，控制台出现未处理异常 | 错误已由请求层提示，但 Promise 仍向上抛出 | 全局 errorHandler 忽略已提示的接口错误 |
| 后端重新构建后启动报模块缺失 | 增量编译缓存与清空输出目录冲突 | 关闭 TypeScript 增量编译 |

## 8. Windows 部署脚本

### 8.1 真实 Windows 上发现的问题

第一版脚本交给用户在 Windows 上运行时，在第 6 步"初始化数据"失败：

```
prisma/seed.ts:8:10 - error TS2305: Module '"@prisma/client"' has no exported member 'CalendarType'.
prisma/seed.ts:8:46 - error TS2305: Module '"@prisma/client"' has no exported member 'UserStatus'.
prisma/seed.ts:17:40 - error TS2694: ... has no exported member 'UserCreateInput'.
```

**原因**：脚本依赖 `npm ci` 时 `@prisma/client` 自带的 postinstall 自动执行 `prisma generate`。该钩子先写入一个不含任何数据模型的占位客户端，再执行生成，生成失败时吞掉错误（以退出码 0 结束），而 npm 默认不显示依赖的安装脚本输出。同一次运行中 `migrate deploy` 成功，说明引擎下载正常，因此更可能是 Windows 特有的文件占用问题（npm 并发执行依赖安装脚本、杀毒软件锁定引擎文件等），在 Linux 上不会出现，所以此前的验证没有发现。

**复现**：在 Linux 上全新克隆、`npm ci` 后，按 postinstall 的做法把 `node_modules/.prisma/client` 替换为占位客户端，再运行 `npm run seed:demo`，得到与用户完全相同的 3 条错误（行列号一致）。

**修复**：

1. `server/package.json` 增加 `"postinstall": "prisma generate --no-hints"`。根项目的 postinstall 在所有依赖安装完成后才执行，失败时 `npm ci` 直接报错并显示原因；
2. `setup.ps1` 安装依赖后用 `Assert-PrismaClient` 检查客户端是否为真实生成，否则重新生成一次，仍失败则按 EPERM / 下载失败 / 路径过长给出提示；`reset-password.ps1`、`dev.ps1` 运行前同样检查；
3. 中途失败后重新运行可以续上（见 8.3）。

### 8.2 排查全部脚本发现的其他问题

| 问题 | 处理 |
|---|---|
| 中途失败后重跑，因 `.env` 已存在被当作"再次运行"：不再询问演示数据、不显示管理员账号（随机生成的密码永远看不到） | 部署成功时写入标记文件 `server/.setup-complete`，未成功过时按首次部署处理 |
| 后台服务依赖任务计划程序的"失败时重新启动"，但该设置只在任务无法启动时生效，程序启动后以非 0 退出码结束不会触发；开机时 MySQL 未就绪会导致平台一直停止 | 启动器改为守护进程：子进程退出后按 5→10→20→40→60 秒自动重启；子进程预加载 `parent-watch.cjs`，启动器被结束后自行退出，不留孤儿进程 |
| `service.ps1` 在提权后的新窗口中出错会立即关闭窗口，看不到原因；菜单中任一命令出错都会退出脚本 | 提权窗口退出前等待按键；菜单中每个操作单独捕获错误后回到菜单 |
| `service.ps1` 的"查看日志"在菜单中不显示任何内容（日志行进入管道后被丢弃） | 改为直接输出到控制台 |
| `start.ps1` 的 `catch [UriFormatException]` 不会生效，`DATABASE_URL` 缺失时误报"无法连接 MySQL" | 新增 `Get-DatabaseConfig` 统一校验解析，`setup`、`start`、`backup` 共用 |
| 输出中有 Prisma 弃用警告、"Update available 6.x -> 8.0.0-rc" 提示、Accelerate 广告和 npm 弃用警告，易被误认为出错 | 移除 `package.json#prisma`；设置 `CHECKPOINT_DISABLE`、`PRISMA_HIDE_UPDATE_MESSAGE`；`prisma generate --no-hints`；`npm ci --loglevel=error` |
| 用户的解压路径约 174 个字符，接近 Windows 260 字符上限 | 路径超过 120 个字符时给出提示 |
