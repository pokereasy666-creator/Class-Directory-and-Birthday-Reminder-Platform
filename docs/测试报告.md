### 3.1 随机交叉验证

另写一个思路完全不同的参照算法：从起始日期开始逐日向后扫描，把每一天的公历日期转换成农历，检查是否命中生日。它与被测实现方向相反（公历→农历 vs 农历→公历），也不依赖"候选年份 Y−1、Y、Y+1"的推理。用固定种子生成 600 组随机输入（公历 / 农历各约一半，农历中约 1/5 为闰月出生，日期覆盖三十；起始日期覆盖 2020—2034 年），两者结果必须完全一致。

### 3.2 变异测试

为确认测试确实能发现错误，人为在实现中植入以下缺陷，每次只植入一个并运行测试：

| 植入的缺陷 | 测试结果 |
|---|---|
| 农历候选年份去掉 Y−1 | 2 个用例失败（含随机交叉验证） |
| 农历候选年份去掉 Y+1 | 2 个用例失败（含随机交叉验证） |
| 三十出生遇小月不回退到二十九 | 2 个用例失败（含随机交叉验证） |
| 平年 2 月 29 日不回退到 2 月 28 日 | 3 个用例失败（含随机交叉验证） |
| 农历年表换算偏移一天 | 6 个用例失败 |
| 忽略闰月 | 2 个用例失败（含随机交叉验证） |

所有缺陷都被发现。

> 过程记录：交叉验证最初使用的线性同余随机数取的是低位（`seed % n`），而模 2 的幂的线性同余生成器低位周期极短，`rand(2)` 只是 0、1 交替，导致 600 组用例覆盖面很差，植入"去掉 Y−1"的缺陷时随机测试没有失败。改为取高位后，随机测试能够发现上表全部缺陷。

## 6. 性能

生日查询对全班 n 人逐个计算，复杂度 O(n)。实测农历生日计算的耗时：

| 场景（50 个农历生日，一次查询） | 优化前 | 优化后 |
|---|---|---|
| 首次 | 约 120 ms | 约 14 ms |
| 后续 | 约 85 ms | 约 2.5 ms |

优化前的瓶颈在于农历库只缓存最近一个年份，而算法需要交替查询三个年份；优化方法见系统设计 3.4 节。

## 7. 测试中发现并修复的问题

| 问题 | 原因 | 处理 |
|---|---|---|
| 农历生日查询慢（50 人约 85ms） | 农历库单年份缓存被交替访问击穿 | 按农历年缓存月表，查表换算 |
| 随机交叉验证未发现植入的缺陷 | 随机数取低位，周期过短 | 改为取高位 |
| 未登录时返回英文提示 "Unauthorized" | 框架默认异常信息 | 自定义 JWT 守卫，返回"请先登录""登录已过期" |
| 按钮操作中接口报错时，控制台出现未处理异常 | 错误已由请求层提示，但 Promise 仍向上抛出 | 全局 errorHandler 忽略已提示的接口错误 |
| 后端重新构建后启动报模块缺失 | 增量编译缓存与清空输出目录冲突 | 关闭 TypeScript 增量编译 |

## 8. 未覆盖的内容

- **真实邮件发送**：测试环境没有 SMTP 服务器，只验证了未配置 SMTP 时邮件功能自动关闭、站内通知不受影响。部署时需用真实邮箱账号验证一次。
- **导出文件名**：无头 Chromium 会把非 ASCII 的下载文件名替换为 `download`（用 ASCII 文件名对照验证过是浏览器行为）。服务端响应头 `filename*=UTF-8''班级通讯录-日期.xlsx` 和前端解析逻辑已单独验证，桌面浏览器中的中文文件名未在本环境验证。
- **定时任务的触发时刻**：提醒逻辑通过接口手动触发做了完整测试；"每天 8:00 自动触发"依赖 cron 库，只验证了启动时成功注册。
- **前端单元测试**：前端未编写组件级单元测试，由类型检查与界面走查覆盖。
